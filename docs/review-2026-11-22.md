# Codebase review (2026-11-22)

A whole-repo review of `main` at 7dc50b0 (PR #29) for AI slop, duplication, security, correctness, tests,
accessibility, performance and CI. Five reviewers read the code (auth and public surface; photos, deploy, CI and
dependencies; backend modules; web; docs). Each finding was checked against the source, and the main security ones
were checked again by hand.

**Totals: 0 critical, 0 high, 13 medium, 45 low (58).** Nothing found lets a stranger read a client's photo or
another client's list. The mediums are a public OOM, privacy gaps in what uploads and backups keep, an email-cap
bypass, and requests that fail without the client being told.

Paths starting `java/` are under `backend/app/src/main/java/com/lookmate/app/`. Size: S < 30 lines, M < 200, L more.

## Medium

**1. Public inspiration confirm can OOM the backend.** intake · `java/intake/IntakeService.java:131-161` · S
`POST /api/public/match-requests/{token}/inspiration/confirm` needs no login. It reads up to 25 MB, strips it and
re-checks it with no `PhotoDecodes` turn (the stylist path at `java/stylists/PhotoService.java:143-158` takes one),
inside a transaction that holds a row lock and a connection while it downloads from R2. Each call holds 75-100 MB;
the heap is about 460 MB (`deploy/compose.prod.yml:115`, `MaxRAMPercentage=60`), so 3-5 concurrent confirms from one
IP's 10 hourly requests kill the API for everyone (`ExitOnOutOfMemoryError`). Fix: take a decode turn outside the
transaction and answer 503 on busy, as `PhotoService` does.

**2. Abandoned portfolio uploads keep the unstripped original, and the backup copies it.** stylists, deploy ·
`java/stylists/PhotoService.java:111-137`, `deploy/backup/backup.sh:9,71` · S+S
Stripping happens only at confirm. A stylist who uploads and then closes the tab leaves a `PENDING_UPLOAD` row whose
R2 object keeps its GPS and device EXIF. Nothing sweeps these, and after an hour `backup.sh` copies every non-intake
object into `photos-age/`, which is kept forever. Fix: back up only keys whose `portfolio_photo.status in
('READY','HIDDEN')`, and sweep `PENDING_UPLOAD` rows older than the upload TTL plus an hour (row to DELETED, object
deleted).

**3. Photos deleted from the app stay in backups forever, against the terms.** deploy · `deploy/backup/backup.sh:8-14,69-71`;
`backend/app/src/main/resources/terms/stylist-2026-11-20b.txt` item 4; `docs/data-retention.md:41`; `docs/hosting.md:138` · M
A stylist deletes a photo because the person in it asked; encrypted copies stay in `combpatible-backup/photos-age/`
and off-site, and `restore-photos.sh` can bring them back. The terms promise 30 days including backups. **Decision:
make it true** (above). Fix: the backup job prunes `photos-age/` objects whose photo is no longer READY/HIDDEN, once the
object lock allows it, or a 30-day lifecycle rule with a periodic re-copy of live photos. Whichever is simpler; keep
age encryption. Update `data-retention.md` and `hosting.md` to match.

**4. The per-address email cap can be reset, and the email carries attacker text.** intake ·
`java/intake/MatchRequestRows.java:146-155`, `java/intake/IntakeService.java:183-188`, `java/intake/IntakeController.java:40`,
`java/notify/ClientEmails.java:110-111` · M
The cap counts clients whose *current* email is the address. Set victim@x on a request (email sent), then set junk@y:
the victim's count is back to 0. One IP does this ~60 times a day, so the victim gets ~60 emails a day instead of 5,
each greeting "Hi <legacy firstName>", up to 40 characters of any text. That's a spam relay through our Resend sender.
Fix: count from `email_message` by recipient over 24 h (or log addresses as they're set), and stop accepting
`firstName` on create (the quiz stopped sending it on 2026-11-20).

**5. A FAILED request shows "Matching you with stylists" forever.** intake, web · `java/intake/IntakeService.java:210`;
`web/src/pages/public/MatchStatusPage.tsx` · S/M
`case MATCHING, IN_REVIEW, FAILED -> Stage.MATCHING`. A request fails when its photo can't be embedded after
max-attempts (`MatchingFlowTest.java:263`). The page keeps polling and promising matches, with no email. **Decision:
retake prompt** (above). Fix: a new `FAILED` stage in the client view, the retake-and-browse copy on the page, the
failure visible on `/admin/matches`, and a flow test.

**6. `deploy/prod-check.sh` queries Rawmark's `photo` table.** deploy · `deploy/prod-check.sh:25-33` · S
`photo`, `checked_at`, `retake_reasons`, `side` and `storage_key` don't exist here, so every run prints `relation
"photo" does not exist`. The real tables are `portfolio_photo`, `portfolio_photo_embedding`, `embedding_attempt`,
`match_request` and `email_message`. Fix: replace the block with checks for portfolio photos by status (and
`PENDING_UPLOAD` over 1 h), the embedding backlog and failures, match requests by status (NEW with a photo over 15 min,
MATCHING over `matching-stuck-after`, latest FAILED with `status_reason`), the email outbox (overdue PENDING, stuck
SENDING, latest FAILED) and inspiration retention lag (undeleted after 31 days).

**7. Every `@Scheduled` job shares one thread.** notify · `backend/app/src/main/resources/application.yml` (no
`spring.task.scheduling.pool.size`); jobs at `java/matching/MatchingConfig.java:23`, `java/notify/NotifyConfig.java:32`,
`java/intake/InspirationRetention.java:74`, `java/intake/ClientContactRetention.java:71`, `java/notify/EmailRetention.java:65` · S
A matching pass with Bedrock can take minutes; meanwhile the 20 s email sender doesn't run, and a hung provider call
holds every email. Fix: `spring.task.scheduling.pool.size: 4` in the base document.

**8. The embedding fallback can't recover from a SQL error.** matching · `java/matching/EmbeddingWorker.java:52-57,84-97` · M
Claim, provider calls and saves share one transaction. A failed statement (constraint, vector dimension after a model
change) aborts it, the whole batch rolls back including `embedding_attempt`, and the same photos are reclaimed every
pass forever. The batch also holds row locks and a connection across blob reads and provider calls. Fix: claim and
commit, embed outside a transaction, save each result in its own short transaction.

**9. Admin pages and the Auth0 SDK ship to every client.** web · `web/src/App.tsx:9-14`, `web/src/AuthProvider.tsx` · M
A client opening `/m/:token` on a phone downloads the 491 kB vendor chunk (147 kB gzip, with @auth0) and a 102 kB main
chunk that is mostly admin code, and Auth0 runs a session check on a page where nobody signs in. Fix: `lazy()` the
admin and tracking pages, mount `Auth0Provider` only around the signed-in routes, split @auth0 out of vendor.

**10. The results page says "This page updates by itself" after polling has stopped.** web ·
`web/src/pages/public/MatchStatusPage.tsx:26,109-114`, `web/src/useLoad.ts` · S
`usePoll` gives up after 20 minutes without telling the page. If matching is slow the client waits on a page that
never changes, even after the list is published. Fix: `usePoll` returns `gaveUp`; the page offers Reload and points to
the email.

**11. The PWA manifest points at icons that don't exist.** web · `web/vite.config.ts:23-25` · S
`icon-192.png` and `icon-512.png` aren't in `web/public`, so Chrome won't offer Install and home-screen adds get a
letter tile. Fix: add the PNGs from `favicon.svg`.

**12. Two docs say production admin MFA is on.** docs · `docs/local-dev.md:216-217`, `docs/hosting.md:181` · S
CLAUDE.md and `docs/auth.md:112-113` say it is off on the pilot server until real stylists join. Fix: point both at
`auth.md`, with the turn-it-back-on step.

**13. `compose.prod.yml` doesn't pass `MATCHING_PROVIDER` and friends to the backend.** deploy ·
`deploy/compose.prod.yml:37-56`; `docs/hosting.md:83` · S
The handoff says to set `MATCHING_PROVIDER` in the server `.env` to switch to Bedrock; it would have no effect, nor
would `MATCHING_REVIEW_BEFORE_PUBLISH` or `RETENTION_*`. Fix: add the pass-through lines and say in the env table which
variables reach the app.

## Low

### Security and privacy

**14. Caddy logs stylist invite tokens in clear.** deploy · `deploy/Caddyfile:53`, `java/identity/AdminOrgController.java:62` · S
The redact regex covers `api/invites` and `m` but not the SPA route `/invite/<token>`. Anyone with log access can join
that org as a stylist for 7 days. The comment at `Caddyfile:47` says invites are redacted; `DeployConfigTest.java:53`
tests only the API path. Fix: add `invite` to the alternation and the test.

**15. `/api/public/book/{token}/{matchId}` has no per-IP limit.** intake · `java/intake/PublicRateLimit.java:47,67`,
`java/intake/IntakeConfig.java:23` · S
Every other public route answers 429. This one runs a token lookup, a 4-table join, an advisory lock and two counts
per call. Fix: add it to `BROWSE_PATHS` and the `browse` check, with a test.

**16. The create limiter spends day tokens on refusals, and its eviction can go O(n) per request.** intake ·
`java/intake/PublicRateLimit.java:73-74,88-90` · S
`Math.max(take(day), take(hour))` takes from both buckets even when one refuses, so 10 creates plus 10 refused retries
lock shared salon wifi out for the day. Past 50k keys `removeIf` walks the whole map on every request and frees
nothing; an idle day bucket evicted after an hour resets that IP's daily cap. Fix: check both, then take both;
evict on a timer or use a bounded expiring cache.

**17. A corrected client email doesn't cancel the email queued to the wrong address.** intake ·
`java/intake/IntakeService.java:173-184` · S
The PENDING email to the typo address still goes out, with the client's private link. Fix: cancel the request's
PENDING emails before queueing the new one.

**18. Images are built from `main` without waiting for CI.** ci · `.github/workflows/images.yml:74-79`, `deploy/deploy.sh:35-36` · S
Two green PRs that conflict when merged still get images, and `deploy.sh` with no argument deploys them, migrations
included. Fix: trigger `images.yml` on `workflow_run` success of CI.

**19. No dependency or image vulnerability scanning.** ci · `.github/workflows/ci.yml`, `images.yml` · S
`npm audit --omit=dev` is clean today; the full audit shows 4 moderate build-only advisories (glob, minimatch via
workbox-build). Nothing would flag a runtime one. Fix: `npm audit --omit=dev --audit-level=high` in the web job,
Trivy on the built images.

**20. Dependabot misses the Dockerfiles and `deploy/compose.prod.yml`.** ci · `.github/dependabot.yml:14-16` · S
Base images (temurin, node, caddy, postgres/pgvector) and the pinned rclone get no PRs. Fix: `docker` for `/backend`,
`/web`, `/deploy/backup`; `docker-compose` for `/deploy`.

**21. The backend and backup containers lack Caddy's hardening.** deploy · `deploy/compose.prod.yml:87-116` · S
No exploit path today (non-root, no ports), but a compromised JVM keeps default capabilities and a writable root, and
the backup service has no `mem_limit` beside Postgres. Fix: `no-new-privileges`, `cap_drop: [ALL]`, `read_only` with
a `/tmp` tmpfs, a memory limit on backup.

**22. Admin refresh tokens in `localStorage`.** web · `web/src/AuthProvider.tsx:16` · M · **Deferred** until real stylists join (decision above)
An XSS could take an admin's rotating refresh token. Unlikely (CSP has no `unsafe-inline`, no
`dangerouslySetInnerHTML`), but it's the most valuable secret the app holds and MFA is off on the pilot.

## Checked and fine

- **Endpoints:** `/api/public/**` permitAll, `/api/admin/**` ROLE_ADMIN, other `/api/**` authenticated, the rest
  denyAll. Org routes go through `OrgAccess.require`; photos, matches and events are looked up by org, so no IDOR
  between stylists. A link token reaches only its own request.
- **ADMIN and MFA:** ROLE_ADMIN only from the roles claim with `amr` mfa or the MFA claim, except the documented pilot
  flag. No issuer means every token is refused. Tested.
- **Link and invite tokens:** 32 bytes from SecureRandom, only SHA-256 stored, expiry enforced in SQL, invites
  single-use with a 7-day TTL.
- **Booking redirect:** https only, host required, no user info, rebuilt from the authority, `utm_source=combpatible`,
  `no-referrer` and `no-store` on the 302. No open redirect.
- **Client IP:** `getRemoteAddr()` with framework forwarding behind Caddy, which drops a client-sent
  `X-Forwarded-For`. All SQL is bound.
- **Photos:** presigned PUT 10 min (type, length, `If-None-Match` signed, server-chosen keys) and GET 15 min, only for
  READY/HIDDEN photos of LIVE stylists or a confirmed inspiration photo. No public URLs. JPEG/PNG stripping drops
  EXIF, XMP, IPTC, text chunks and trailers. Header-only size limits. Inspiration retention deletes storage then row.
- **Caddy:** narrow CSP, HSTS, nosniff, `frame-ancestors 'none'`, 1 MB API bodies, actuator limited to health.
  Postgres not published in prod.
- **Backups:** age-encrypted; the private key is off the server; plaintext only in a cleaned temp dir.
- **Secrets:** only blank `.env.example` templates tracked; `VITE_` values are public Auth0 settings.
- **CI:** actions pinned to SHAs, read-only permissions, Testcontainers required, ModularityTest, OpenAPI and
  api-types checks run.
- **Matching:** SKIP LOCKED claims tested for double-claims; scoring and hair-compatibility math tested and
  symmetric; "no email means no emails" covered by `AutoPublishFlowTest`.
- **Web:** no `dangerouslySetInnerHTML`, no service-worker caching of `/api` or R2, reduced motion honoured, the
  native dialog traps focus. Nothing outsider-visible says LookMate. Build, lint and 76 tests clean.
- **Dependencies:** `npm audit --omit=dev` clean. No Gradle dependency CVEs we could name with confidence (Boot 4.1.2,
  Modulith 2.1.2, AWS SDK 2.59.2, metadata-extractor 2.22.0, Sentry 8.64.0, springdoc 3.2.0).
